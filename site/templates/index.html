What OpenADR is for

A utility or grid operator needs flexible load to move: charge later, curtail now, follow this price curve. OpenADR is the standard it uses to say so. A VTN (Virtual Top Node) publishes programmes and events; a VEN (Virtual End Node) — a charge point, a battery, a heat pump, a building controller — reads them, acts, and reports back.

Version 3 replaced 2.0b's SOAP with REST and JSON. Version 3.1, released in 2025, added push over MQTT, object privacy, and plain string targets. This crate implements 3.1, and ships both ends of it. The protocol in fifteen minutes →

What it does that the alternatives do not

Object privacy on every path

A charge point operator must never learn which other groups an event targets — that is a competitor's dispatch schedule. One Access value decides visibility for REST reads, webhook delivery and MQTT topic routing, and renders itself into the WHERE clause so filtering happens inside the query rather than over a page that has already been cut.

On a broker the VTN answers the authorization callback too, so one VEN cannot subscribe to another's topic — which the specification requires and leaves entirely to the implementer.

A dispatch instruction cannot be lost

Notifications are written to a transactional outbox in the same transaction as the object that caused them, then delivered by a leased dispatcher. There is no window in which an event exists and nobody has been told — and nothing in OpenADR can say afterwards that a notification was never sent.

Every queued entry names the transport that owns it, so an entry nothing can send is reported as undeliverable rather than deleted as sent.

Interoperability is measured

openadr conformance runs forty-eight black-box checks against any OpenADR 3.1 VTN, each citing the sentence of the specification it tests. A check that could not run is reported as skipped and never counted as a pass.

Run against another implementation, it found six required divergences there — and two defects here.

Money is decimal

Payload values are prices, fees and capacities — settled money. Value::Number holds a rust_decimal::Decimal, not an f64, so 0.1 + 0.2 == 0.3 holds exactly and a tariff round-trips through JSON unchanged.

The specification's sentinels are types

P9999Y means "forever" and 0001-01-01 means "now". Left as strings they are one forgotten comparison away from a schedule that runs for nine thousand years. Here they are Duration::Forever and StartTime::Now — the match arm has to exist.

Polling is the normal case, and push is a hint

Because in every deployment surveyed polling is what happens: Dutch grid-aware charging re-reads a 48-hour window, Belgian NetFlex clients poll their schedule, Californian price clients poll hourly. Every GET carries an ETag, and both the client and the VEN runtime use it — a quiet cycle costs a 304 with no body.

MQTT push is here on both ends, and the VEN never reads a notification's payload: it wakes the loop, the loop re-reads from the VTN. A broker can cost a VEN latency; it cannot cost it correctness.

The intervals an event does not list still exist

A tariff that loops for ever and a capability forecast that declares no intervals at all are both ordinary indexing into one sequence: interval fifty thousand of an hourly tariff running since 2020 costs two multiplications, not fifty thousand clones.

It is what makes repeat: -1 and numIntervals: 48 mean what the User Guide's own worked scenarios say they mean.

Authentication is a trait, with three real backends

Fluvius forbids OAuth2 and requires mutual TLS. Californian price servers are anonymous. Dutch grid-aware charging uses Keycloak. A VTN that assumes one of those cannot serve the others, so this one runs its own token endpoint, validates somebody else's JWTs against a JWKS, or accepts a pre-shared token.

It runs where the load is

The wire model, the payload schema and the domain core are no_std + alloc and build for thumbv7em-none-eabihf and WebAssembly — the appliance-class VEN the specification's own security chapter has in mind. No C toolchain anywhere in the tree, and cargo deny keeps it that way.

The single binary is actually single

--tls-cert and --tls-key serve HTTPS directly, so a site controller needs no reverse proxy in front of it; --tls-client-ca refuses a connection whose certificate that CA did not issue, during the handshake.

And it describes itself: GET /openapi.json covers the VTN you fetched it from, with the broker endpoints absent when there is no broker — named by openapi_url in the mDNS record, so a VEN that finds the VTN can read its API without being told anything else.

A VTN in one command

{%- filter markdown(inline=false) | safe %} ```console $ cargo install openadr --features vtn,client,internal-auth,sqlite $ openadr vtn --database ./openadr.sqlite \ --client-hashed "bl-1:$(openadr hash-secret "$BL_SECRET"):bl" \ --client-hashed "ven-1:$(openadr hash-secret "$VEN_SECRET"):ven" 2026-02-11T09:00:00Z INFO openadr::vtn: VTN listening addr=0.0.0.0:3000 base_path=/openadr3/3.1.0 ``` {% endfilter %}

That is a complete OpenADR 3.1 VTN: every endpoint, the OAuth2 client-credentials grant with Argon2id-hashed secrets, object privacy, durable storage, a notification queue, GET /metrics and a dead-letter view — one binary and one file. Swap --database for a postgres:// URL and the same binary is the shared, multi-instance deployment.

The same binary is also the client, so nothing above needs a second tool:

{%- filter markdown(inline=false) | safe %} ```console $ openadr post programs --data '{"programName":"grid-aware-charging"}' $ openadr get events --program prg-00000001 --active $ openadr watch events --targets group1 # prints only when something changes ``` {% endfilter %}

And a VEN that acts on what it reads

{%- filter markdown(inline=false) | safe %} ```rust let ven = VenRuntime::with_meter(client, config, HouseMeter); ven.register().await?; // idempotent, and checks the VTN's clock loop { ven.sync().await?; // conditional: a quiet cycle is a 304 if let Some(segment) = ven.active_at(ven.now()) { act_on(&segment.payloads); // priority already resolved } ven.submit_due_reports().await?; // each window filed exactly once ven.wait_for_work().await; // wakes early on an MQTT notification } ``` {% endfilter %}

Registration, resource reconciliation, one conflict-resolved timeline per programme, randomizeStart applied from a seed, a clock-skew guard, and report scheduling that survives a restart — across a looping tariff and against intervals the event never lists. What the load does and what the meter reads are yours; the rest is not your problem.
